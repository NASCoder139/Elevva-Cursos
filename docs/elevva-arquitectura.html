Elevva — Arquitectura y Despliegue

Guía completa: cómo está montada tu plataforma de cursos online

1. La arquitectura: 3 servicios separados

Tu plataforma no vive en un solo lugar. Está dividida en 3 piezas que viven en proveedores distintos y se comunican entre sí:

   Usuario (navegador)
         │
         ▼
   ┌──────────────────────┐
   │  CLOUDFLARE PAGES    │  ← Frontend (React)
   │  elevva-cursos       │     HTML/CSS/JS estático
   │  .pages.dev          │
   └──────────┬───────────┘
              │ peticiones /api/...
              ▼
   ┌──────────────────────┐
   │       RENDER         │  ← Backend (NestJS)
   │  elevva-cursos       │     Lógica, autenticación, pagos
   │  -render.onrender    │
   │  .com                │
   └──────────┬───────────┘
              │ consultas SQL
              ▼
   ┌──────────────────────┐
   │        NEON          │  ← Base de datos (PostgreSQL)
   │  ep-noisy-shape...   │     Usuarios, cursos, lecciones
   └──────────────────────┘

2. Qué hace cada servicio

Cloudflare Pages — donde vive el frontend

  • Hosting de archivos estáticos con CDN global (tu sitio carga rápido en cualquier país).
  • Qué hace: sirve los archivos .html, .css, .js que vite build generó.
  • No ejecuta lógica de servidor. Es solo una página que se descarga al navegador y ahí corre React.
  • Cómo se actualiza: cada git push a la rama main dispara un build automático.

Render — donde vive el backend

  • Es un PaaS (Platform as a Service): le das código Node.js, él lo ejecuta como servidor 24/7.
  • Qué hace: corre tu API NestJS. Recibe peticiones HTTP (/api/auth/login, /api/courses, etc), las procesa, consulta la base de datos, y devuelve JSON.
  • Cómo se actualiza: igual, cada git push lo redeploya automáticamente.

Neon — donde vive la base de datos

  • PostgreSQL "serverless": una base de datos en la nube que no tienes que administrar.
  • Qué hace: guarda toda tu data persistente — usuarios, cursos, lecciones, pagos, etc.
  • Tu backend de Render se conecta a ella mediante el DATABASE_URL.

3. Las variables de entorno

Las "env vars" son configuración que cambia entre desarrollo (tu PC) y producción (la nube). El código es el mismo, pero las URLs/secretos cambian.

En Render (backend)

VariablePara qué sirve
DATABASE_URLCómo conectarse a Neon (incluye usuario, contraseña, host)
JWT_SECRETLlave secreta para firmar tokens de sesión de usuarios
JWT_REFRESH_SECRETLlave secreta para los refresh tokens
BACKEND_URLSu propia URL pública (para construir links en emails, callbacks de pago)
FRONTEND_URLURL del frontend → CORS la usa para permitir peticiones solo desde ahí
MP_ACCESS_TOKEN / PAYPAL_CLIENT_IDCredenciales de las pasarelas de pago

En Cloudflare Pages (frontend)

VariablePara qué sirve
VITE_API_URLA qué URL pegarle cuando React quiera datos. Apunta al backend de Render + /api
⚠️ Detalle clave: las variables que empiezan con VITE_ se embeben en el JavaScript del navegador durante el build. Si las cambias, hay que redesplegar — porque están dentro del archivo .js ya generado, no se leen en tiempo real.

Por qué las URLs van "cruzadas"

Frontend  →  apunta a  →  Backend   (VITE_API_URL = URL de Render)
Backend   →  apunta a  →  Frontend  (FRONTEND_URL  = URL de Cloudflare, para CORS)
Backend   →  apunta a  →  DB        (DATABASE_URL  = URL de Neon)

Cada servicio necesita saber la dirección del otro porque viven separados.

4. CORS — por qué tantos problemas con las URLs

CORS (Cross-Origin Resource Sharing) es una protección del navegador. Por defecto, JavaScript solo puede llamar APIs en el mismo dominio donde corre.

Como tu frontend (elevva-cursos.pages.dev) y backend (elevva-cursos-render.onrender.com) están en dominios distintos, el navegador bloquea las peticiones a menos que el backend diga explícitamente "permito peticiones desde tal origen".

Por eso en main.ts del backend tienes:

app.enableCors({ origin: FRONTEND_URL, credentials: true })

Y por eso fue crítico que FRONTEND_URL no tuviera barra final (/) — la comparación es literal.

5. Limitaciones del plan gratis

Cloudflare Pages — el más generoso

  • ✅ Ancho de banda ilimitado
  • ✅ 500 builds al mes
  • ✅ Sin "spin down" — siempre disponible al instante
  • ⚠️ Solo archivos estáticos (no puedes correr Node.js aquí)

Render Free — el cuello de botella

  • ⚠️ Spin down tras 15 min sin tráfico: el servidor se "duerme". La siguiente petición tarda ~50s en despertar (cold start).
  • ⚠️ 512 MB de RAM — suficiente para NestJS, pero si la DB crece o hay muchas peticiones concurrentes puede crashear.
  • ⚠️ 750 horas/mes gratuitas — un servicio 24/7 ocupa ~720h, da justo para uno solo.
  • ⚠️ Sin disco persistente: los archivos subidos (uploads/) se pierden en cada redeploy. Para producción real necesitas S3 / Cloudflare R2.

Neon Free

  • ✅ 0.5 GB de almacenamiento (suficiente para miles de cursos/usuarios)
  • ⚠️ La DB también se suspende tras inactividad. La primera consulta tarda 1-2s en despertar.
  • ⚠️ 1 proyecto, 10 ramas

6. Cómo se ve un request real (login del usuario)

Cuando un usuario hace login en https://elevva-cursos.pages.dev/login:

  1. Cloudflare sirve el HTML/JS al navegador (instantáneo, está cacheado globalmente).
  2. El usuario rellena el formulario y React hace POST a https://elevva-cursos-render.onrender.com/api/auth/login.
  3. Render despierta su servidor si estaba dormido (~50s la primera vez), recibe la petición.
  4. El backend valida CORS (origen = elevva-cursos.pages.dev ✓ permitido).
  5. Consulta a Neon: SELECT * FROM users WHERE email = ...
  6. Si las credenciales son correctas, firma un JWT con JWT_SECRET y lo devuelve.
  7. El frontend guarda el token y redirige al dashboard.
